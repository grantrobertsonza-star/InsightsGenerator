# D2: dashboard configuration (29 October 2026)

Status: **D2a implemented, ready for independent review** (configuration and the recogniser's input). The screens
that use it are D3; figures from the owning modules are D3 with D2b's new measures. Follows D1
(`claude/tracker-roles.md`).

## Grant's decisions (29 October 2026)

1. Settings are saved **per programme** ("Ok, lets start with programme"); a project in no programme keeps its
   own.
2. **Weighted by default** when the file has a weight ("weighting will probably be more of an expectation than the
   rule in market research data"). The weight is the app's default weight rule (`defaultWeight`); the researcher
   can choose unweighted, and that is kept as a choice.
3. Inputs are mostly **raw files** ("it will 90% be standard raw files": SPSS, Excel, text, R, Python). A JSON
   codebook such as the packs' metadata.json is unlikely in practice; it was made for checking.

## What the recogniser reads (`src/lib/trackerInput.ts`)

The dictionary, every variable's answer labels as calculations see them (engine action `value_labels`), and the
question number, type and set of the strongest confirmed codebook entry. See `claude/tracker-roles.md`, Input.

The codebook reader keeps those three fields when a codebook gives them: columns found by header name only
(question / question id / qid; question type; MR set), a question column taken as an ID only when its cells are
short codes (a "Question" column holding wording stays the label), and a type that is none of the known kinds
kept as written (`questionTypeAsWritten`), never mapped to a guess. A column headed universe, filter, base, asked
of, routing, condition, derivation, selected value or unit is never the answer list (Grant's tracker codebooks
had attribute items reading "aware_b01=1" as an answer). A JSON codebook's separate `labels` list
([variable, variable label, code, answer label] rows) gives the answers of a variable whose entry has none.
Stored in `instrument_items.question_meta` (**migration 0131**); before it the read says "The question numbers,
types and sets it gives were not saved: the database needs migration 0131", and everything else works as before.

## Stored configuration (`tracker_dashboards`, migration 0132)

One row per programme (or per project in no programme; a check allows exactly one scope, and a unique index per
scope). Only the researcher's **choices** are stored (main brand by code, answers that are not brands, a question's
stage or "not a stage", CSM roles by variable, weighted or not, hidden charts), with where and when they were last
made, by whom, and `suggested`: what was suggested then (rules version `d1-2026-10-29`). The suggestion itself is
worked out from each wave's file whenever the dashboard opens, so a new wave gets its own suggestions.
- **Saves and resets** are a compare-and-swap on the **scope and revision the screen read** (`scopeKey`:
  `programme:<id>` or `project:<id>`; "none saved yet" is its own expected revision; two first saves cannot both
  win). The scope is rechecked under the project row's lock: a project moved to another programme (or into or out
  of one) since the view is refused (`moved: true`) and changes neither scope (Codex D2A-F01: on the revision alone,
  a stale view of programme A replaced programme B's choices at an equal revision). A refused save returns the
  scope the project is in now, its revision and choices; nothing is written.
- **Choices are checked on the server** against this wave (codes in its brand list, per-brand question groups,
  stage names from the one stage list `FUNNEL_STAGES` in `trackerRoles.ts` (Codex D2A-F02), variables in the file, a
  weight to weight by). A choice unchanged from the stored one is kept even when this wave cannot apply it,
  including "weighted" on a wave without a weight (D2A-F03), so resaving from one wave never drops another wave's
  choice.
- **Reset to suggested** clears the choices and keeps them in `previous_choices`, with `reset_at`.
- Deleting a programme deletes its choices (cascade); deleting a wave's file or project keeps them.
- Before migration 0132 the dashboard shows the suggestion and refuses saving with that reason.

## Applying choices to a wave (`src/lib/trackerDashboard.ts` `resolveDashboard`)

By identity: brand codes, question groups, variable names; never labels or positions. A choice this wave cannot
apply (a brand code no longer listed, a question or variable missing, weighting chosen for a file with no weight)
is listed under "needs a choice" with the reason, and its stored value is kept. The recogniser's open questions
are listed until a choice answers them: a CSM question (satisfaction, recommend, stay, switch, drivers) by an
applicable choice of its role, a variable this file has or an intentional none (D2A-F04); a carried choice this
file lacks keeps the question; a "is this partly labelled list 0 to 10?" question only by choosing that variable. Main brand: asked once, **pre-filled** with the brand the programme or
project name names (whole words, longest name), shown as pre-filled and still asked until chosen.

## Generation (D3)

Figures come from the owners: the crosstab engine for funnel and attribute percentages (unrounded, base stated),
the NPS and driver modules with the dashboard's filters, bases and weight. A module that has not run or failed
shows that state. No figure is computed in the dashboard layer.

D3a brand overview (implemented 29 October): `loadBrandOverview` (src/lib/trackerOverview.ts). One Cross tab per
wave file through `computeCrosstab`, the same computation `buildCrosstab` saves, so opening a dashboard adds no
table to the file. A share is the unrounded percentage of the selected code (`selectedCode`): the code whose label
says selected, yes, mentioned, chosen, ticked or checked; code 1 of a 0/1 variable; otherwise "not available" with
the reason, never 0. Base: the unweighted valid answers; effective base when weighted. One measure per stage; a
stage two questions claim is listed as unresolved, not guessed. The previous wave is the wave file just before
this one in `loadProjectWaves` order, resolved with the same saved choices; none (earliest wave, or the file is
not a wave) and failed (its figures could not be read) are said as such, never shown as no change. Comparators:
five brands, the client's first when chosen, then the file's list order, labelled as suggested; the researcher's selection on
screen is not saved yet.

Every standard tile is always shown (Grant, 29 October 2026: "what is missing generates a blank tile ... and then
the user can correct that"): seven funnel tiles (awareness to frequent usage) and five CSM tiles (satisfaction, NPS,
likely to stay, likely to switch, driver priority). A tile with no question, or two questions claiming it, is blank
with "Choose a question", which opens Customise at that choice; the choice is saved for the programme like any other.
A blank tile can also be hidden (Grant: for a dashboard used in a report). Hidden tiles are the `hidden` choice
(ids `stage:<stage>` and `csm:<tile>`), saved at once from the stored choices, never with an unapplied draft; "Show
hidden tiles" clears them. A hidden tile that has a figure again shows anyway: only blank tiles are hidden.

D3a CSM tiles: `csmOverviewFigures` (src/lib/trackerCsmFigures.ts) through the owners, with `table: "compute"` so
nothing is saved: the distribution and `summarizeSeries` (satisfaction mean and top-two box, likely to stay top-two
box, likely to switch 8 to 10 on a 0 to 10 scale and top two on a shorter one), the NPS tool's own score and
interval, and driver analysis of satisfaction on the chosen drivers. Don't-know and not-applicable answers are
outside the base as in a Cross tab. Missing (no variable) and failed (the owner's reason) are separate states.
D3b (29 October): the company each customer rates is a CSM role (`company`, trackerRoles.ts): a single-choice
question whose wording names a company, bank, provider, insurer, network or operator and is not a rating, with an
answer list of names (not a scale), or a coded question with no stated scale; two candidates are a question. It is
looked for only in a CSM file without a brand list (a brand list compares brands itself, and brand names such as
"Standard Bank" would read as companies). Choices: `csm.company` (the question) and `focalCompanyCode` (the client's
company, refused unless the company question's answer list has the code). Companies come from the answer list by
code ("Other", "None", no-answer codes left out); without an answer list figures by company are not shown and the
screen says why. Each CSM tile carries its figure per company from the same owner split by the company question;
the all-customers figure stays the owner's unsplit reading. Change against the previous wave (`csmChangesAgainst`):
the box share or the NPS score, for all customers and each company by code, only when both waves read the same
question by name; otherwise no change, with the reason. Screen: "Showing" chooses all customers or one company for
the tiles (the client's company by default), a "By company" table lists every company with its change, and driver
priority stays for all customers, said so. Not yet: on-page filters, a split of driver priority by company. A company's change against the previous wave is shown only when both waves'
company questions are the same and its code names the same company in both answer lists (`codeNamesDiffer`, the
brand funnel's identity rule); otherwise the box and mean changes are withheld with the reason (Codex E1-F01).

### D3c Moments & needs (page 02 of the brand dashboard, 29 October 2026)

Grant's design: "Understand category needs, then see which brands come to mind for each." Loader
`loadBrandMoments` (src/lib/trackerMoments.ts), server action `loadBrandMomentsAction`; the page is calculated only
when it is opened. One Cross tab per file through `computeCrosstab` (nothing saved), every relevance option and
every recall cell of a linked moment a row item, with the dashboard's weight (`resolveDashboard`: weighted by default
when the file has a weight) and the file's survey design. Each share is read by `trackerFigures.selectedShareOf`, the
same reading as the brand funnel: the unrounded percentage (`pctExact`) of the selected code (`selectedCode`, by
code, never by label) among the variable's valid answers.

**Recognition** (`trackerRoles.findCategoryMoments`, in `recogniseTracker` as `categoryMoments`): the category moments
question is a group (multiple-response set, else question ID) of yes/no or multiple-response variables that no brand
question or grid claimed, whose option wording equals the wording of the moments grid's items ("<brand> recalled for
<moment>"); at least three options and 60% of the grid's items must each match exactly one item. Wording is compared
on letters and digits, ignoring case; a label that starts with the variable's own name ("relevant_c01. Replacing an
unreliable car", as a CSV with a linked codebook reads) is compared after the name; a variable with no label is read
from its name without the list's first name part. Options worded as no moment ("None of these", "Other") are outside
the moments. Two qualifying lists are "ambiguous"; none is "not_found". The link between the two questions is the
moment's wording (all they share); figures are always read by variable and code.

**Figure contracts.**

| Figure | Numerator | Denominator (base) | Eligible population | Weighting | Missing data |
|---|---|---|---|---|---|
| Category relevance of a moment (left card) | Weighted sum of respondents whose answer to the moment's option is the selected code | Weighted sum of respondents with a valid answer to that option | Everyone asked the question; in the BMW pack all eligible respondents (1,000) | The dashboard's weight when weighting is on (default when the file has one), else 1 | A blank or declared missing value is outside that moment's base only. A respondent who chose "None of these" holds 0 on every moment and **stays in the base** as not selecting. The "None" option itself is never ranked |
| Moment x brand recall (right card) | Weighted sum of respondents whose recall link for that brand and moment (e.g. `cep_c06_b08`) is the selected code | Weighted sum of respondents with a valid answer to that link | All eligible respondents in an all-asked grid (the BMW pack); otherwise those answering | As above | As above. Not personal relevance; no comparison between cells is tested |

Reported with each figure: the unweighted count of valid answers (base); the Kish effective base of the file when
weighted. Ranking: highest unrounded relevance first, equal shares in the question's order; a moment whose share
cannot be read is last and never ranked as 0. Rows of the recall card: the six most relevant moments that have a brand
recall question; a more relevant moment without one is named under the table. Columns: the client's brand, then the
brands compared (the Compare chip, the same selection as page 01, not saved).

**States** (never zeros): relevance question not found, "Not measured" with the reason; two candidate lists, "Mapping
needed"; no moments grid, the recall card "Not measured"; no brand list, recall "Not measured"; relevance not
available, the recall card "Mapping needed" (its rows are chosen by relevance). A file that cannot be read fails the
page with the reason and "Try again"; nothing is shown as empty. There is no screen yet to choose the relevance
question by hand.

Reference values: `trackerMoments.db.test.ts` against `src/lib/__tests__/helpers/moment_reference.py` (pandas over the
same file, written from the pack's specification): all 12 moments and all 120 links of BMW wave 1, weighted and
unweighted, to 1e-6. The pack copy in this repository has no moments rows of `reference_results.json`, so the pack's
own CEP reference values were not compared.

### D3d Brand associations (page 03 of the brand dashboard, 29 October 2026)

Grant's design: "Brand associations: Compare what aware respondents associate with each brand." One card,
"Association profile: Pick-any associations. Each brand uses its own awareness base; these are not agreement
scores." A dot plot: one row per attribute in the grid's order, x axis 0% to 80% (extended to the next 20 above the
highest figure shown when one is higher), one dot per plotted brand (the client's brand larger and blue, the brands
compared from the Compare chip in their own colours, a legend), the client's brand's value printed at the right.
Footnote: "Aware bases: BMW 831 | Mercedes-Benz 801 | ... Positioning model appears only when a supported analysis
has completed." Same chips row as pages 01 and 02. Loader `loadBrandAssociations` (src/lib/trackerAssociations.ts),
server action `loadBrandAssociationsAction`; the page is calculated only when it is opened, nothing is saved.

**Recognition.** The associations grid is the recogniser's grid of kind "associations" (`recogniseTracker`, rule 4 of
claude/tracker-roles.md: "<brand> associated with <attribute>"). The awareness question is the one the dashboard maps
as awareness (`trackerFigures.overviewMeasures`, the same choice as page 01's awareness tile, including the
researcher's saved stage choices).

**Figure contract.**

| Figure | Numerator | Denominator (base) | Eligible population | Weighting | Missing data |
|---|---|---|---|---|---|
| Association share of brand X for attribute A | Weighted sum of respondents aware of X whose answer to A for X (e.g. `attr_a01_b08`) is the selected code (`selectedCode`, by code) | Weighted sum of respondents aware of X with a valid answer to A for X | Respondents aware of X: X's variable in the awareness question equals that variable's selected code. Each brand has its own base | The dashboard's weight when weighting is on (default when the file has one), else 1 | "Don't know" stays in the base, as the pack specifies: a respondent who answered don't know for A (the pack's per-attribute flag `attr_dk_aXX`) holds 0 in X's cell and counts as not associating; an answer code of the association variable itself labelled don't know also stays in the base, as not selected (the request sets `excludeDk: false`). A blank (the pack leaves unaware respondents blank) or a declared missing value is outside the base |

Pick-any: a respondent may give one attribute to several brands, so the shares of an attribute do not add up to 100,
and they are not agreement scores. No comparison between brands or cells is tested; no competitor average or gap is
shown yet.

**Computation.** Through the existing owners, by raw codes: one Cross tab (`computeCrosstab`, not saved) of every
listed brand's awareness variable gives each brand's selected awareness code and the unweighted count aware
(`trackerFigures.selectedAnswerOf`, the same reading as `selectedShareOf`); then one Cross tab per brand of its
association variables, restricted to that brand's aware respondents by an engine filter on the raw awareness code
(`between` the code and itself, never an answer label), with the dashboard's weight and the file's survey design.
Each cell is read by `selectedShareOf`, the reading of the funnel and page 02. At most four brand tables are
computed at once.

Reported: per brand, the aware base (unweighted count aware) and, when weighted, the Kish effective base of the
aware respondents; per cell, the unweighted count of valid answers among the aware.

**States** (never zeros, never all respondents as a fallback base): no associations grid, "Not measured"; no brand
list, "Not measured"; no question mapped as awareness, or two questions claiming awareness, "Mapping needed" (the
base cannot be defined); awareness not asked about a brand, its aware code not told, or not a number: that brand's
cells are n/a with the reason and its aware base n/a; nobody aware of a brand: its cells n/a, base 0; an attribute
not asked about a brand, a suppressed share or a selected code not told: that cell n/a with the reason. The reasons of
the plotted brands' n/a cells are listed under the plot. A file that cannot be read fails the page with the reason
and "Try again".

Reference values: `trackerAssociations.db.test.ts` against `src/lib/__tests__/helpers/association_reference.py` (pandas
over the same file, written from the pack's specification): all 100 cells and every aware base of BMW wave 1,
weighted and unweighted, to 1e-6, and BMW's ten values equal to the pack's published table (section 4.2 of
claude/tracker-packs-role-spec-2026-10-28.md) to two decimals; a boundary file where respondents not aware of BMW
hold BMW associations (not counted), don't know respondents (in the base) and blanks (outside that cell's base).
